# Архитектура

## Структура

```
_Match3/Code/
│
├── Board/
│   ├── Data/            МГНОВЕННОЕ СОСТОЯНИЕ — кто где стоит прямо сейчас
│   │                      BoardState: клетки, захваты сторон, грязные клетки.
│   │                      Мутируется в момент решения: блок занимает целевую
│   │                      клетку с первого мгновения хода, поэтому падающий
│   │                      останавливается об него сразу.
│   │                      BlockRegistry: пул блоков, id блока — его адрес везде.
│   │
│   ├── Operations/      ПРОЦЕССЫ — что происходит и сколько это длится
│   │                      PendingOp: одна операция (Move/Swap/Fall/Destroy),
│   │                      участники + логические таймеры. Единственный источник
│   │                      времени: вью читает Progress, влиять не может.
│   │                      OperationsLayer: тик всех операций, физика падения
│   │                      (непрерывная координата, перехват, следование в столбе).
│   │
│   ├── Flow/            BoardSimulation — конвейер тика и единственная точка
│   │                    мутаций. Событийная очередь: завершение операции порождает
│   │                    следующие (падения, разрушения) внутри того же тика.
│   │
│   ├── Validation/      ActionValidator — можно ли сделать ход. Чистые предикаты:
│   │                    невалидный ход не оставляет следов, откатывать нечего.
│   │
│   ├── Matching/        MergeRules.CanMerge — единственная проверка соседства
│   │                    во всём модуле. DestructionResolver собирает всех жертв
│   │                    тика в одну операцию Destroy — одновременные линии
│   │                    уничтожаются одновременно. Поле никогда не сканируется:
│   │                    матчи ищутся только от dirty клеток, после оседания или действия.
│   │
│   ├── Input/           InputRouter + IInputMode (сменные режимы, сейчас свайп).             
│   │
│   ├── View/            Читает логику. GridView раздаёт визуалы из пула
│   │                    по слотам; BlockSlot двигает блок по Progress операции.
│   │
│   └── Debug/           Оверлей состояния поля (F1/F2). В билд не попадает.
│
├── Session/             SessionController: уровни, победа, переходы, рестарт.
│                        BoardBuilder: сборка поля из уровня или сейва.
│                        SnapshotWriter/SaveStorage: сохранение.
│
├── Configs/             SO-конфиги: уровни, тайминги, изинг и сменные части
│                        блоков (IMatchLogic, IDestructionTrigger, IBlockRule…).
│
├── Background/          Фоновые шары.
│
└── Composition/         Match3Scope (DI), GameRunner (кадр), точка входа.
```

Всё выделено один раз под максимальный размер поля; смена уровня меняет активные границы,
а не размеры массивов. В тике нет ни аллокаций, ни сканов поля.

---

## Кадр

```
GameRunner.Tick()
   dt = Time.deltaTime          <- единственное чтение времени во всём модуле
    |
    +--> InputRouter.Read()      жест -> RequestMove либо ничего
    |
    +--> BoardSimulation.Tick(dt)
    |       таймеры -> события -> ход игрока -> разбор грязных клеток
    |       возвращает InProgress | BecameStable | StayedStable
    |
    +--> GridView.Draw(dt)       вью догоняет логическое время
    |
    +--> если BecameStable:      поле пустое -> следующий уровень, иначе -> снапшот
```

Длительности операций живут в `GameplayConfig` и принадлежат логике: операция завершается по
своему таймеру, что бы ни показывал экран. Вью каждый кадр читает `op.Progress` и отображает:
переезд — лерп с кривой из `EasingConfig`, падение — напрямую из `CurrentY`, разрушение — выбор
кадра спрайтовой анимации. Из той же дробной позиции считается порядок отрисовки, поэтому
перекрытия 3D-нарисованных блоков корректны и в движении.

---

## Жизнь одного хода

1. Свайп → `ActionValidator`: невалидный ход молча отброшен, блок дёрнулся (`Rejection`).
2. Валидный: `BoardState` мутирует **сразу**, создаётся `PendingOp` — дальше ход существует
   только как таймер.
3. Таймер дошёл: под участником пусто → падение; есть опора → клетка помечена грязной.
4. Конец тика: грязные клетки → одна операция `Destroy` на все совпадения сразу.
5. `Destroy` освободил клетки → всё, что висело выше, падает; приземления метят новые грязные
   клетки — каскад крутится, пока есть работа.
6. Операций и событий нет — покой: проверка победы, снапшот.

## Из чего собран блок

Тип (`BlockTypeConfig`) — три сменные части, выбираются в инспекторе (`[SerializeReference]`):

| Часть | Отвечает за | Реализации                                                 |
|---|---|------------------------------------------------------------|
| `IMatchLogic` | какие блоки совпадают | равенство типа; список совместимых                         |
| `IDestructionTrigger` | повод для уничтожения | линия из 3+                                                |
| `IDestructionExpansion` | зона поражения от повода | линия; линия + соседи первого порядка; вся связная область |

Экземпляр (`BlockConfig`) — тип + список `IBlockRule`: правила участия в матче с учётом
направления, например запрет матча сверху («шапочка»). Обе точки сходятся в
`MergeRules.CanMerge`; прямых сравнений типов в коде нет, поэтому новый блок — это новый ассет,
а не новая ветка в логике.

Внешний вид подключается отдельно — `BlockVisualCatalog`: строка на каждый `BlockConfig` — префаб
визуала и цвет для дебаг-инструментов (оверлей, редактор уровней). Логические конфиги про
отображение не знают вообще, связь блок→вид существует только на стороне вью. Итого новый блок —
это `BlockConfig` + строка в каталоге; ни одна из трёх частей не требует кода, если поведение
собирается из существующих реализаций.

## Расширение

| Что добавить | Куда |
|---|---|
| Новый вид блока | новый `BlockConfig` + строка в `BlockVisualCatalog` |
| Новый уровень | новый `LevelConfig` (рисуется кистью в инспекторе) + строка в `LevelSetConfig` |
| Новую логику совпадения | реализация `IMatchLogic`, появится в выпадающем списке типа |
| Новое условие уничтожения | реализация `IDestructionTrigger` |
| Новую форму взрыва | реализация `IDestructionExpansion` |
| Новое правило блока | реализация `IBlockRule` |
| Новый способ ввода | реализация `IInputMode` + регистрация в контейнере |
| Новое движение шаров | реализация `IBalloonMotion` |

Логика тоже легкорасширяема, добавление новых условий, операций или чего либо, не должно вызвать каких либо проблем.

---

## Сохранение

JSON в `persistentDataPath`: уровень, ходы, блоки как `{ConfigId, X, Y}` — по строковому id.
Пишется только в моменты, когда состояние однозначно: точка покоя и старт уровня.
